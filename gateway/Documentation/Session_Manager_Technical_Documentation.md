# Session Manager — Technical Documentation

> **Status:** PASS / LOCKED (2026-06-23)
>
> The Session Manager is responsible for handling user chat sessions, preserving multi-turn context, and managing what-if academic scenarios.

---

## 1. Component Purpose

The Session Manager (`gateway/session_manager.py`) is responsible for:
- Creating and reusing chat sessions
- Persisting session state
- Preserving multi-turn conversation context
- Storing last referenced entities (courses, skills, roles)
- Storing temporary what-if assumptions
- Building an effective `StudentContext` for scenario-aware execution
- Listing session summaries/history
- Deleting sessions safely

**What it is NOT responsible for:**
- Not academic rule calculation (handled by ALE)
- Not KG/RAG/ALE calls
- Not final natural-language response generation (handled by Response Composer)
- Not official registrar data ownership (handled by Student Context Provider)
- Not entity resolution (handled by Query Understanding)
- Not UI rendering

---

## 2. Architectural Boundary

The Session Manager interacts with the following components:
- **main.py / API Gateway:** Handles route endpoints and session setup.
- **Student Context Provider (SCP):** Provides the official base `StudentContext`.
- **Query Understanding (QU):** Resolves entities and extracts contextual elements.
- **Orchestrator:** Coordinates execution across services.
- **Response Composer:** Generates the final natural language response.
- **SQLiteSessionStore:** Persists the session state.
- **schemas.py:** Defines the core data models.

**Important flow:**
1. `main.py` loads a fresh `StudentContext` from SCP every `/chat` request.
2. `get_or_create_session` either creates a new session or loads an existing one.
3. Existing same-student sessions refresh their `student_context` from the fresh SCP context.
4. QU uses `session.last_referenced` and recent turn history to resolve entities.
5. The Orchestrator uses `build_effective_context` for scenario-aware execution.
6. `update_session_after_turn` persists overrides, last references, and turn history after the Composer returns.

---

## 3. SessionState Data Model

The core session entity is `SessionState`, which contains the following main fields:
- `session_id`: Opaque, generated by UUID.
- `student_id`: Ownership identifier. Always checked for safe student-facing operations.
- `session_name`: Auto-generated or user-provided summary of the session.
- `student_context`: The base facts about the student from SCP.
- `last_referenced`: Stores the latest entities referenced in the conversation.
- `overrides`: Temporary assumptions for what-if scenarios.
- `turn_history`: Record of previous messages in the session.

---

## 4. LastReferenced Mechanism

The `LastReferenced` object stores the latest `course_code`, `role_id`, `track_id`, and `skill_id`.
- **Purpose:** Supports follow-up queries like "Can I take it?" or "what about that skill?".
- **Merge-based updates:** Updates are merge-based, not replace-based. Missing fields in a new turn do not wipe out old references.
- **Extraction:** The `Orchestrator.extract_last_referenced` extracts references from resolved `StructuredQuery` entities.

---

## 5. SessionOverrides Mechanism

The `SessionOverrides` object stores temporary assumptions:
- `added_courses`: Courses the student assumes they will take.
- `assumed_failed_courses`: Courses the student assumes they will fail.
- `assumed_passed_courses`: Courses the student assumes they will pass.
- `target_role`: The career role the student is targeting.
- `course_override_type`: A narration/source flag ("planned", "assumed_done", "assumed_failed", "assumed_passed", "gpa_scenario", "none"). Must not be treated as the only logic switch for all overrides.
- `override_action`: Specifies how to apply the override ("accumulate", "replace", "clear").

**Purpose:**
- Supports what-if academic scenarios.
- Temporary assumptions inside one session.
- Does not modify official registrar records.

---

## 6. build_effective_context Semantics

The `build_effective_context` function creates a modified `StudentContext` for the Orchestrator to use.
**Exact order of application:**
1. Start from official base `StudentContext`.
2. Apply `assumed_failed_courses`:
   - Add to `failed_courses`
   - Remove from `completed_courses`
   - Remove from `in_progress_courses`
   - Remove from `zero_credit_courses_passed`
3. Apply `assumed_passed_courses`:
   - Add to `completed_courses`
   - Remove from `failed_courses`
   - Remove from `in_progress_courses`
4. Apply `added_courses`:
   - By default add to `in_progress_courses` as planned courses.
   - Only add to `completed_courses` when `course_override_type == "assumed_done"`.

**Key behaviors:**
- The `base_context` is never mutated.
- `model_copy(deep=True)` / `update` is used to create a safe copy.
- Lists are copied first before modification.
- Deterministic ordered deduplication is used to maintain list stability.
- If the same course appears in both assumed_failed and assumed_passed, "passed" wins because assumed_passed is applied after assumed_failed.

## 7. Session Creation and Reuse

`get_or_create_session` behavior determines session continuity:
- If no `session_id` is provided, create a new session.
- If `session_id` is missing/stale, create a new session.
- If the session exists but belongs to a different student, **do not reuse**. Create a new session and log a safe warning.
- If the session exists and belongs to the same student, reuse it and refresh `student_context` from the fresh SCP context.

**Why this matters:**
- Prevents cross-student data leakage.
- Keeps official student context fresh if SCP data updates.
- Preserves conversation history and assumptions.

---

## 8. Persistence Layer

The Session Manager delegates storage to a `SessionStore` abstract contract:
- `save(session)`
- `load(session_id)`
- `delete(session_id)`
- `get_all_for_student(student_id)`
- `get_summaries_for_student(student_id)`
- `delete_all()`
- `delete_all_for_student(student_id)`

**SQLiteSessionStore implementation:**
- Has a specific table with index on `student_id`.
- Stores session data as a JSON `session_blob` via Pydantic serialization.
- Tracks `last_updated` timestamp.
- If `load()` encounters a corrupted blob, it returns `None`.
- `get_all_for_student()` skips corrupted blobs.
- Summaries returned by `get_summaries_for_student` are ordered by `last_updated` descending.

---

## 9. Session History and Summaries

- `get_student_sessions` returns lightweight summaries designed for sidebar/history UI.
- `get_session_history_for_student` returns full turn history but verifies ownership.
- The old `GET /session/{session_id}/history` endpoint is disabled with a `410 Gone` status.
- The safe endpoint to use is: `GET /students/{student_id}/sessions/{session_id}/history`

---

## 10. Deletion Mechanism

The deletion mechanism implements two distinct product-level features:

**Student-facing:**
- The UI shows a chat history/sidebar.
- Each session can have a three-dot menu with a "Delete session" button.
- It calls: `DELETE /students/{student_id}/sessions/{session_id}`
- The backend verifies ownership before deleting.
- Deletes only one specific session.

**Developer-only:**
- Used to cleanup test sessions before/after integration testing or before deployment.
- Global cleanup: `DELETE /dev/sessions`
- Per-student cleanup: `DELETE /dev/students/{student_id}/sessions`
- Both are strictly protected by dev mode (`APP_ENV=dev` or `DEV_MODE=true`).
- Outside dev mode they return `403 Forbidden`.
- Global delete must never be shown in the student UI.

**Function hierarchy:**
- `SQLiteSessionStore.delete(session_id)`: low-level delete primitive.
- `delete_session_for_student(student_id, session_id)`: safe student-facing delete.
- `delete_all_sessions_for_student(student_id)`: developer cleanup for one student.
- `delete_all_sessions_global()`: developer global cleanup.
- `clear_all_sessions()`: backward-compatible alias (if present).

## 11. API Endpoints

- **`GET /students/{student_id}/sessions`**
  - **Purpose:** List session summaries.
  - **Ownership:** Safe, filtered by `student_id`.
  - **Expected:** Returns lightweight summary list ordered by last updated.
  - **Failure:** None.

- **`GET /students/{student_id}/sessions/{session_id}/history`**
  - **Purpose:** Get chat turns.
  - **Ownership:** Verifies ownership.
  - **Expected:** Returns `turn_history`.
  - **Failure:** Returns 404 if not found or cross-student mismatch.

- **`DELETE /students/{student_id}/sessions/{session_id}`**
  - **Purpose:** Delete a single session.
  - **Ownership:** Verifies ownership before deletion.
  - **Expected:** Deletes and returns 200/204.
  - **Failure:** 404 if not found/mismatched.

- **`DELETE /dev/students/{student_id}/sessions`**
  - **Purpose:** Delete all sessions for a specific student.
  - **Ownership:** Developer only.
  - **Expected:** Clears store for that student.
  - **Failure:** 403 Forbidden outside dev mode.

- **`DELETE /dev/sessions`**
  - **Purpose:** Global cleanup.
  - **Ownership:** Developer only.
  - **Expected:** Clears the entire store.
  - **Failure:** 403 Forbidden outside dev mode.

- **`GET /session/{session_id}/history`**
  - **Purpose:** Deprecated/disabled.
  - **Expected/Failure:** Returns 410 Gone.

## 12. Logging and Privacy

**Logging principles:**
- No full `StudentContext` logs.
- No full transcript dumps.
- No raw grade lists.
- No raw query text in `/chat` logs.
- `/chat` logs `query_len` only.
- Ownership mismatch logs: `owner=<redacted>`
- Dev global delete is logged at `WARNING` level.
- Delete count logs are acceptable.
- Corrupted blobs are logged as warnings without dumping the session data.

---

## 13. Error Handling

- **Stale/missing session_id:** Creates a new session gracefully.
- **Cross-student session mismatch:** `get_or_create_session` will create a new session instead of failing.
- **Cross-student delete/history:** Returns safe not found/error behavior.
- **Corrupted SQLite blob:** Skipped/treated as not found.
- **Dev endpoints outside dev mode:** Returns 403.

## 15. Known Non-Issues / Design Decisions

- Multiple delete functions are intentional layering, not multiple student features.
- The student UI only needs the delete-one-session capability.
- Developer cleanup is an API/dev utility only.
- Assumptions are strictly session-local and do not alter registrar records.
- Session Manager does not resolve entities; it stores already-resolved IDs provided by QU/Orchestrator.
- Session Manager does not decide academic eligibility or graduation status.

---

## 16. Carry-Forward Notes

- The UI still needs to wire the student-facing delete-session menu later during UI/API integration.
- Developer cleanup endpoints should remain disabled in production.
- If a future authentication layer is added, session ownership should use authenticated identity, not only the path `student_id`.
- If storage moves from SQLite to a production DB, keep the same `SessionStore` contract.
